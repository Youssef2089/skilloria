La phrase qui résume

Sur ses trois points figés — filtres SQL, puis Cohere, Claude seulement au dépôt ; notes 0-10 converties une fois ; notes clées sur l'empreinte — le moteur est conforme. Mais l'expert ne peut pas s'en servir aujourd'hui : l'écran qui ouvre une mission demande à la base une colonne supprimée le 1er septembre, et c'est le seul écran d'où l'on postule. Derrière, ce que le moteur coûte est mal compté — le tarif du reranker n'a pas de source, les recherches web de la vérification ne sont pas comptées —, et une relance dont le run échoue est soldée quand même. Le reste de ce document dit où, avec quelle preuve, et ce qui reste à trancher.

Le flux cache les annonces expirées, mais le moteur les note et les paie dans les deux sens, et crée des matches vers des annonces mortes. Une annonce expirée dont le run est resté inachevé est rejouée jusqu'à cinq fois par le rattrapage. Sens expert → annonces : lib/matching/run-for-expert.ts:227-241 ne filtre que status = 'published'. Rattrapage : next_unfinished_matching_run (20260912200000_verrou_run_et_unicite_notifications.sql:65-77) idem. Sens annonce → experts : lib/matching/index.ts:207-234 ne teste ni le statut ni l'expiration de l'annonce. Mesuré : 12 lecteurs du filtre d'expiration (activePublishedOrClause / isActivePublished) dans app/ + lib/, 0 dans lib/matching/. Base : 6 annonces publiées, 6 expirées, 0 active. La règle « le moteur ne note que published ET non expirées » est écrite dans 20260921000010_inacheves_hors_annonces_expirees.sql:26-28 — le code ne l'applique pas (§E.29). Rien à trancher sur le fond : le filtre SQL « gratuit » manque des deux côtés. À décider : le rattrapage abandonne-t-il une annonce expirée en cours de rejeu (elle sort alors de la supervision par construction) ?
D3ZÉRO FOIS · SILENCE « J'ai modifié mon profil, aucune annonce n'arrive, et personne ne le sait. » Une relance dont le run échoue (interrupteur fermé, clé absente, plafond, lot en échec) est soldée quand même : rien ne la rejoue. Avec le moteur éteint — l'état de cet environnement — chaque relance est consommée par un run qui s'arrête à la première garde. Le sens annonce fait l'inverse et rejoue. app/api/cron/expert-relance/route.ts:101-102 et app/api/me/sync-matching/route.ts:211-215 : solderRelance après le run, quel que soit verdict.status. Rien n'équivaut, côté profil, à matching_completed_at ; matching_relance_health() ne voit donc rien. Côté annonce : lib/matching/index.ts:436-465 laisse le run inachevé, rejoué ≤ 5 fois. Arbitrage 1. Que devient une relance dont le run est empêché ou partiel : la garder (donc la rejouer toutes les 5 min tant que le moteur est éteint) ou la solder en le disant à l'expert ?
D4SUPERVISION MUETTE L'administrateur ne peut pas savoir si les deux pilotes du moteur (rattrapage, relance) atteignent l'application, sauf pour la tranche 21 h – 4 h. Le reste de la journée, le journal n'a aucun verdict HTTP. Base : 9 853 lignes pour les deux pilotes depuis le 03/09, 7 201 jamais réconciliées (73 %). La réconciliation ne passe qu'à 03 h 15 et 03 h 45 (20260823000000_purges_rgpd_pg_cron.sql:346-364), et la réponse pg_net disparaît en ~6 h (:176) : un passage de 10 h du matin n'a plus de réponse à copier la nuit suivante. Les lignes réconciliées disent 200, « Aucun run inachevé », « Aucune relance ». Arbitrage 2. Réconcilier plus souvent pour les tâches à 5 minutes (au prix de lignes dans le journal pg_cron), ou accepter un journal aveugle aux trois quarts et l'écrire.
D5COÛT INVISIBLE Le plafond du reranker (200 $/mois) protège d'un montant qu'il ne sait pas compter : le tarif n'a pas de source fournisseur, et l'unité journalisée est le document. Base, ai_model_tarifs : rerank-v4.0-fast, 0,000002 $, source = « Valeur retenue par le code depuis lib/matching/rerank.ts » — la ligne dit elle-même qu'elle ne vient pas d'une grille. Code : lib/matching/rerank.ts:390 journalise unites: lot.length (des documents). NON VÉRIFIÉ dans le dépôt : la grille Cohere. Si elle facture par unité de recherche (une requête × jusqu'à 100 documents, un document long comptant plusieurs fois), la journée normale coûterait ≈ 0,32 $ contre 0,005 $ comptés (§8). Arbitrage 3. Relire la grille, poser usd_par_unite avec sa source, et décider si l'unité journalisée reste le document ou devient l'unité de recherche. Le signal tarifs_non_verifies de la supervision existe ; il ne dit pas lequel des quatre tarifs est faux.
D6COÛT INVISIBLE Chaque « Publier mon profil » lance une vérification Claude avec jusqu'à 4 recherches web ; les recherches ne sont pas comptées par le plafond, seuls les jetons le sont. lib/verification/expert-verification.ts:597-604 enregistre aiOut.usage ; la seule forme de consommation possible est jetons ou unités (lib/ai-consommation.ts:31-35). D7DEUX FOIS Deux recherches lancées à quelques secondes pour le même expert (deux onglets, bascule puis ouverture croisée, relance cron pendant un run direct) paient deux fois Cohere, et l'une des deux peut finir en « la recherche n'a pas pu aboutir » sans raison visible. Deux réconciliations concurrentes insèrent la même paire : UNIQUE (publication_id, profile_id) (00000000000000_baseline.sql:1949) → 23505 → run en erreur → issue lecture_en_panne. La reprise (matching_notes_partielles) atténue le double paiement sans le fermer. Arbitrage 5. Un bail par profil sur le chemin direct (même forme que cron_run_leases), ou accepter le double paiement borné par le plafond horaire (20/h).
D8ZÉRO FOIS Une candidature dont le jugement n'a pas eu lieu parce que la fonction a été tuée reste sans note, sans pitch, et la place incluse n'est pas attribuée — sans compteur ni rattrapage. L'organisation voit une place vide et paiera un dévoilement manuel pour ce qui lui était dû. app/api/candidatures/route.ts:301-401 : un seul after(), aucun rejeu ; la panne n'est comptée que si le modèle a répondu non (:354-368) ; devoilementInclus est sauté avec le jugement. 5Question A — où les deux sens se rejoignent, et ce qu'une asymétrie ferait

Le point de rencontre est une table, matching_notes_partielles : clé primaire (publication_id, profile_id), colonne model, colonne empreinte (20260911200000_reprise_notation.sql:28-35 ; 20260922000000_empreinte_des_notes.sql). Les deux sens y écrivent après chaque lot payé (reprise.ts:96-128, 159-191) et y lisent avant de payer, en ignorant toute ligne d'un autre modèle ou d'une autre empreinte (:52-73, 199-233). Le sens annonce solde son brouillon quand son run s'achève (index.ts:467-471) ; le sens expert ne solde jamais — la purge de 24 h s'en charge.

Conséquence mesurée sur le partage lui-même : il est surtout à sens unique. Une note écrite par un run d'expert sert un run d'annonce qui suit dans les 24 h ; une note écrite par un run d'annonce disparaît à la fin de ce run, et ne sert donc à aucun run d'expert.

Si la symétrie est fausse — ce que le dépôt suppose et n'a jamais mesuré (recette ①)

La note de (requête = annonce, document = profil) et celle de (requête = profil, document = annonce) ne seraient pas les mêmes. Alors, pour une même annonce : ① deux familles de notes dans un seul classement — les profils notés par le run de l'annonce et ceux dont la note a été reprise d'un run d'expert ne seraient plus comparables entre eux, ce qui rouvre à l'intérieur d'une annonce la comparaison que le fournisseur interdit entre deux requêtes ; ② un palier qui bascule sans qu'aucun texte ait changé — la réconciliation met à jour la note et le palier d'un match existant (reconcile.ts:208-226), donc un run de l'autre sens peut faire passer un match de « forte » à « normale », et inversement ; ③ une notification décidée par le sens qui a tourné en premier, puisque « forte » déclenche l'envoi. Ce qui décide, comme la recette l'écrit : que l'écart réordonne, pas qu'il soit non nul.

Quel plafond mord en premier

  • Aucun plafond d'argent ne mord dans une journée normale. Le plafond Claude (100 $/mois) est le premier menacé, et c'est l'analyse de CV qui le consomme, pas le moteur : ≈ 150 CV par jour le feraient franchir dans le mois. Le plafond du reranker est inatteignable au tarif de la base.
  • Ce qui mord en premier, ce sont les gardes anti-abus : 3 analyses de CV par 24 h et par expert (429), 20 déclenchements par heure et par expert (429, compté dans relance_overruns), et le fournisseur lui-même (429 → un seul nouvel essai, puis le lot est perdu et le run inachevé).
  • Les alertes par acteur (2 $/profil, 10 $/organisation) ne se déclenchent pas dans ce scénario ; elles ne bloquent rien de toute façon.

Les déclencheurs sans plafond

  • Publier sur une offre à publications illimitées (business, elite) : chaque publication = un vivier entier + une porte Claude. Publier, clôturer, republier mille fois dans la journée coûte ≈ 4 $ de Claude et 0,2 $ de reranking comptés (≈ 2 $ si facturé à l'unité, NON VÉRIFIÉ) — et c'est le plafond commun qui finit par fermer l'IA pour tous (D12).
  • Approuver un expert (admin) : un run par approbation, sans temporisation — un administrateur qui approuve cent profils lance cent runs.
  • Le rattrapage : jusqu'à cinq runs pour une annonce qui échoue, atténués par la reprise des notes.
